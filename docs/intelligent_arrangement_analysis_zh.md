# yovoice 智能编曲问题分析（2026-10-19）

## 1. 范围、版本和证据

本报告区分三个对象：官方 `v0.3.0`（提交 `8892f72`）、先前的智能编曲预览实现，以及从官方标签建立的本地整合工作树。2026-10-19 已将整合版 `0.3.1-preview.1` 覆盖安装到原有唯一安装目录并启动；这是基于官方版制作的本地定制预览，并非作者发布的官方版本。不能把浏览器预览、启动成功或假音频测试当作真实模型、真实插件的完整实机验收。

数据库兼容性是已证实的启动根因：官方 v0.3.0 存储层最高识别数据库版本 1，而预览版使用版本 4。17:09—21:24 的原安装版日志反复记录“数据库版本 4 高于当前应用支持的版本 1”，服务随后退出。安装登记虽还显示旧预览版，目录中的程序实际已被自动更新为官方 v0.3.0，两个入口共用同一目录和数据库。此次先验证数据库副本，再备份安装文件与数据库，使用不含音频内核的更新包覆盖同一目录。22:34 的 `state.open` 无错误、`service.ready` 与后续作品保存记录证明启动已恢复；没有把 v4 库改成 v1，也没有另建第二个安装版本。完整迁移回退演练、桌面功能与真实生成验收仍需单独完成。

证据来自[官方 v0.3.0 发布说明](https://github.com/leemysw/yovoice/releases/tag/v0.3.0)、该标签的[助手进程源码](https://github.com/leemysw/yovoice/blob/v0.3.0/internal/assistant/assistant.go)和[助手工具源码](https://github.com/leemysw/yovoice/blob/v0.3.0/internal/workbench/assistant_tools.go)，以及本地 `internal/workbench/ai_arrangement.go`、`arrangement_materials.go`、`arrangement_ai.go`、`arrangement_render.go`、`instrument_discovery.go`、`web/src/features/arrangement/arrangement-workspace.tsx` 的逐段审查。复现时只读取原始数据库；临时诊断文件已从工作树移除。

本机原始数据的 `PRAGMA user_version=4`，有 20 个作品、11 个音源、3 个含编曲方案的作品、0 条已准备 AI 乐句、0 个乐队预设。11 个音源对应的全部采样文件存在，但“文件存在”不能证明音色、音域、奏法和许可足以完成指定作品。三个含方案的作品都没有拼合后的时间线。固定目录中有笛子 8 个 `sustain` 采样、二胡 9 个 `sustain` 采样、古筝 34 个 `pluck` 采样；标为“箫（模拟）”的 56 个采样不能被当成真实箫录音。

## 2. 工作流逐段审计

| 阶段 | 用户期待 | 当前实现与断点 | 严重性 |
| --- | --- | --- | --- |
| 输入 | 指定时长、民乐、奏法、真实/AI/混合、参考音 | 有输入框和来源模式；未形成统一、可机器校验的约束对象，参考音与风格约束没有贯穿各阶段。 | P1 |
| 音源盘点 | 优先使用库中已下载且真正可用的源 | 规划前会列出“至少一份文件存在”的真实源；未逐音符核对音域、奏法、文件和品质。模拟箫被刻意排除，故“库里有箫”与“有真实箫”不是一回事。 | P0 |
| 整曲规划 | 段落、乐句、乐器、真实/AI 来源稳定落盘 | 模型返回 JSON，经结构校验和部分指定乐器检查；服务端会匹配源 ID。模型仍可规划大量库中没有的乐器；计划乐器名和角色没有作为下一步写谱的强约束。 | P0 |

| 编辑与导出 | 手工修正后仍可重拼、工程可携带 | 时间线、曲谱和部分音源归档已接通；重拼会给旧编曲轨静音而非覆盖。VST 预设和插件二进制不可随工程归档；准备好但尚未拼合的 AI 音源在官方资源页不完整可见。 | P1 |

### 一次真实的整合回归：智能编曲页面没有进入保存会话

官方 `useDraftSession` 只在作品编辑、版本记录等“打开作品”的页面开启自动保存；新导航把智能编曲做成独立页后，入口有了，但工作台的 `setActive` 仍只识别 `create/history`。因此页面中的 `change({arrangementInput})` 当次 React 状态看起来正确，切页或重启后却不能保证写入 `draft.save`。浏览器复现为输入需求并替换乐器，切到音源库，刷新后需求为空。整合工作树已把 `arrangement` 纳入活动会话，并用该场景复测；这说明集成的关键是**状态生命周期**，不仅是菜单显示和代码能编译。

### 另一处实际阻塞：AI 乐句已生成，前端仍判“缺音源”

AI 备料把整句音频登记到 `ArrangementMaterials`，并不作为单音采样登记到 `InstrumentSources`。原前端拼合预检只查后者，因此即使句音频存在，也可能在调用后端拼合前报“箫 · AI”等缺源；后端实际上支持读取对应句音频。整合工作树已让预检识别当前作品、所选模型、乐句位置和计划哈希一致的已准备材料，缺失材料仍报错，文件存在性最终由后端核验。新增回归覆盖“已准备可继续、未准备仍阻塞”；本轮编曲页面 **20 项全部通过**，另全量 Go、前端 lint/build 通过。未用真实音频模型验收这条链路。

## 3. 根因排序与可证伪条件

1. **计划与写谱是两份独立生成的真相（P0）**。证据是两个用户作品被 `arrangementUnits` 拒绝、旧写谱提示与计划没有同一声部 ID。可证伪条件：对真实失败作品采用统一声部 ID 与逐乐句音符校验后仍在同一处失败。
2. **“已下载”与“适用此乐句”混为一谈（P0）**。当前准备标志多看名称、样本数量和奏法，最终逐音符绑定才检查音高及力度；真实箫要求与模拟箫库存冲突。可证伪条件：对每个音符预检文件、音域、奏法和授权后仍出现“已下载但不能用”。
3. **AI 音频不是从同一乐谱严格合成（P0）**。文本音频模型无法保证精确音符与起止时间；只验证时长是弱条件。可证伪条件：以实际导出的分轨音频做音高、节拍、声源泄漏检测，持续满足规格。
4. **自动寻源覆盖度不足、错误来源混杂（P1）**。真实录音稀缺；Openverse 结果、Freesound 原站、许可、格式和音高验证任一失败都会表现为“下载/寻源失败”。可证伪条件：为每步保留结构化失败码后，失败都指向单一网络故障。
5. **新旧产品的数据和页面演进没有版本契约（P0）**。官方 v0.3.0 数据库最高支持版本 1，预览数据为 4；直接安装官方版使用原资料目录时会出现“数据库版本 4 高于当前应用支持的版本 1”。官方页面又把普通编曲移至“音乐生成”二级页。可证伪条件：新版本使用真实 v4 数据目录启动并完整保留全部预览数据、作品和可编辑引用。

## 4. 官方 v0.3.0 对智能编曲的真实影响

官方更新给了三个可复用基座：

- **Ocho** 提供现成的对话循环、会话、技能、网页检索、文件/命令工具及应用内 MCP 工具。这是发展为编曲调度助手的合适入口，但当前应用工具白名单没有音源盘点、采样审核、编曲规划、逐句备料、VST 绑定、拼合等工具。
- **YuE2 ABC 旋律谱** 提供看谱、编辑、试听、撤销和按谱生成的能力；可以作为旋律或和弦参考，不能直接代替带乐器身份、来源和时间线的多声部编曲中间表示。需定义 ABC/MIDI/多轨计划之间的转换及不可表达信息。
- **资源、日志、模型设置、交互式 API** 让音源占用与错误诊断更有落点，也方便自动化验收。但预览工程的 AI 乐句和插件预设需要纳入资源引用和导出语义；不能仅把新菜单嵌入旧代码。

官方也增加了迁移成本：普通“编曲生成”已在“音乐生成”内，智能编曲应作为独立入口并与它共享作品/曲谱层；直接覆盖安装会因数据库版本不兼容而失败。`ChatGPT (Codex)` 是普通 AI 服务的一个 CLI 提供者；当前 `assistantConfig` 明确拒绝让 Ocho 使用该格式。因此“设置里可用 Codex”不等于“Ocho 就运行在 Codex CLI 上”。

## 5. Ocho 究竟是什么

从官方源码看，Ocho **不是只有聊天框**。Go 服务按需启动单独的 `ocho` 进程，使用 `stream-json` 往返一轮轮消息；进程内 MCP server 暴露受控的 yovoice 工具。其通用工具白名单包含 `Skill`、文件读写/搜索、`Bash`、`WebFetch`、`WebSearch`，Windows 还包含 PowerShell；系统提示限定应用数据只能通过 yovoice 工具修改。每轮有界面上下文、工具事件、超时、取消、会话与偏好记忆。它属于**有工具调用循环的 agent/harness 架构**，和 Codex 的“模型 + 工具 + 状态循环”同一大类，但实现、权限、能力边界并不等同。

目前 Ocho 可以读作品、写词写谱、设置参数、启动现有生成、查询状态，且代码上允许联网搜索和在专属工作目录操作文件。它**不能仅靠现有应用工具**完成“搜民乐样本 → 核验许可/音高 → 导入音源库 → 固定曲谱声部 → 调用 VST → 拼合验收”的闭环；在外部网页找到链接也不会自动成为合格、可追溯的音源。内置子 agent、后台任务和自动记忆被禁用，产品偏好由 yovoice 自己存。是否能对某次 DeepSeek 请求可靠使用网页搜索，仍需在安装版以该服务实测；源码中的工具开放不等于网络和模型每次都能成功调用。

| 能力层 | 官方已有 | 智能编曲缺口 |
| --- | --- | --- |
| 模型推理与循环 | Ocho 子进程通过 `stream-json` 多轮工具调用，DeepSeek 可按 OpenAI 兼容配置接入 | 需要限定编曲任务的步骤、预算、失败恢复和阶段报告；仅有对话不能保证任务完成。 |
| 应用内操作 | `list/get/create/update/generate_work`、查模型、状态、旋律谱、导航、偏好及确认卡 | 工具集没有智能编曲计划、库存、源绑定、采样下载、VST 预设、拼合和工程验收的专用操作。 |
| 外部信息 | `WebSearch/WebFetch` 及工作目录内文件/命令工具在白名单 | 搜到网页只获得候选，真实许可证、采样格式、音域、奏法与安全导入必须由后端核验。 |
| 长任务 | 应用生成任务可查询状态；Ocho 会话可取消 | 智能编曲批量下载/生成/渲染仍是前端顺序轮询，缺持久可重启的任务图。 |
| 安全边界 | 删除和部分敏感操作使用 `propose_action` 确认卡；系统提示限制应用数据操作 | 新领域工具应遵守同一边界，不能让模型直接用 shell 写数据库或凭网页描述安装插件。 |

## 6. 当前结论与未完成验证

首要问题是**计划、乐谱、素材没有共享一个可校验的声部/乐句契约**，所以修好下载仍无法完成现有两个作品。其次是音源“存在、真实、可奏、合规”的状态没有在规划前统一检查。官方 Ocho 能当交互式编曲调度前端，但需要新增受限的领域工具和可恢复工作流，不能直接把它当现成的全自动编曲系统。

整合工作树已补写谱防线：智能编曲写谱请求附带获批计划的乐器/角色/小节和服务端分配的声部 ID；生成结果在交给界面前运行与拼合同一套声部覆盖校验；无效结果会要求模型修正一次并报告具体错误。新规划的 section/phrase/part 已有稳定 ID，曲谱轨道可用 `partIds` 指向跨乐句的计划声部；新计划不再用同名乐器猜测对应关系。保存无歧义的旧工程时可补齐并绑定 ID，有歧义或缺音符时保留原数据并记录原因。同名声部及两类旧工程迁移测试已通过；早先定向浏览器验证逐步扩展到全量 127 项。这是结构性绑定的第一步，仍没有做到按乐句独立生成与局部重试，也不能自动补出已经保存的两份失败工程所缺音符。

仍待实机验收：用户指定的真实箫、琵琶轮指/挑弹样本品质；DeepSeek 规划和写谱的实际输出稳定性；ACE-Step/YuE2 分句音频的音高与时间同步；VST 整轨渲染及预设恢复；项目归档与回退恢复；Windows 安装版完整功能回归。当前唯一安装已恢复启动，智能编曲整体仍处于实验性阶段，不能据此宣称整条工作流已可用。

## 7. 下载为何反复修复仍失败：与小宝乐队的具体差异

小宝乐队本地检出提交为 `4450128`，其 `public/library.json` 保存已知乐器 ID、采样地址、字节数和哈希。`server/app.mjs` 先检查工程所需 ID 是否安装，按乐器 ID 合并并发下载；`server/download.mjs` 直接下载清单文件，校验大小、哈希、音频头，再以临时文件原子替换。它的常规演奏路径不依赖先去开放搜索引擎搜出一件乐器。其乐谱也直接引用库内乐器 ID，采样选择再按奏法、音高、力度层和轮换录音执行。因此它更容易形成“谱 → 已知乐器 → 已知文件”的确定链路；源码不能证明它在任意网络环境均不会下载失败。

yovoice 的整合版已经存在两条不同路径，不能继续统称“下载 CC0”：

| --- | --- | --- | --- |

## 8. 补充发现：缓存与失败恢复仍可能破坏编辑闭环

`arrangement_ai.go` 的 `arrangementJobHash` 输入只有 brief、速度、拍号、调、乐句名、小节范围、乐器、角色和奏法；没有曲谱音符、音符修订或条件 MIDI。缓存命中另比较作品、模型和乐句索引。由此可推断：只修改谱中旋律而不改上述字段，旧 AI 乐句仍可能被当成就绪。这与“手动改谱后重新演奏”不一致；对于自由氛围素材可以容许复用，但 UI 必须明确它不跟谱。后续应区分 `score_conditioned` 与 `free_audio`，前者缓存键必须包含当前乐句音符与条件编码器版本，后者显示需重新审听。

同一文件的批量 AI 备料先把所有结果留在内存，全部成功后才统一登记；中途失败时清理本批已生成文件。这意味着“第 4 句失败”可能丢掉本批前三句成果。当前并非持久任务图，关闭页面后也缺少可靠的批次恢复契约。应按乐句校验并提交成功资产，批次记录子任务状态，失败只重试受影响乐句。

VST 的界面试载还有一项易误判的证据：`scripts/vst-host/main.py` 为 Decent Sampler 的单音诊断临时构造合成测试样本。它能证明插件接收 MIDI 并输出音频，**不能证明真实民乐音色包已经加载、可保留预设或可生成整轨**。这应在产品中标为“宿主连通测试”，另设“当前预设试听”和“整轨渲染验收”。
