# AI 音源生成：开发验证记录（2026-10-21）

## 状态与范围

本记录对应智能编曲 AI 音源生成的开发代码，**不是完整验收或安装发布说明**。既有官方基座为 v0.3.1，当前已安装定制版为 Preview.4，本轮仍在开发验证。源码开发检查点不得被描述成完整可用版。

本轮范围以用户最终确定的 AI 音源生成方案为准：独立乐句与可演奏 AI 音色；默认按谱，由确认后的采样器执行音符；保留模型直接谱条件生成和自由音频。混音系统重写、听音大模型和 Ocho 架构改造不作为本轮新增范围。

## 已实现的服务链路

1. 每个 AI 声部独立保存生成内容、模式、实现方式、声音类别、模型、长度和尾音设置。
2. 服务端预检合同记录原调性、归一调性、相关音符指纹、模型版本、引擎版本、语义帧预算及采样覆盖。
3. 器乐禁止不需要的人声和其他配器；无词合唱使用人声条件，不再与纯器乐参数相冲突。
4. 普通歌曲接口保留原规则；编曲通过专用请求白名单设置 YuE2 语义长度或 ACE-Step 时长。
5. 生成原片先登记，检查与派生文件分开；保留摘要、返回长度、截断标志、请求和各次候选。最多自动额外重试两次；显存不足暂停该项。
6. 按音高、力度区间、奏法和持续时长建立采样需求；代表采样先试听确认，再展开其余采样。精确音高映射不靠扩大移调范围减少任务。
7. 用户确认的单音可进入 AI 音色库；合唱和自由乐句保持音频片段形态，不登记到人物声音库或冒充器乐单音。
8. 已确认健康素材可复用；派生文件、原片及采样映射纳入工程归档和引用管理。

以上是实现状态，真实模型适用性仍须按下面的证据分别判断。

## 本轮定位并修复的原因

### 单音谱与请求长度冲突

旧单音条件用固定 60 BPM、4/4 小节，约 1.730769 秒音符后补到 4 秒的休止，而请求只有约 2.24 秒。现在从受限 ABC 可表示的整数速度和拍号中选择条件，使整张单音谱不含多余主体休止；回读音符与总时长，允许的量化差不超过 0.02 秒。

这里改变的是模型候选的条件谱，不改变用户作品的音符或节奏。

### 速度、表情和缓存

原采样器乐句实现把本句移到第一小节后丢掉段落速度和力度渐变。现在保持原时间坐标演奏，再提取当前乐句。缓存包含本句各小节实际速度、拍号、调性与音符；其他乐句的独立速度变化不使本句失效。

模型直接生成的受限 ABC 尚不支持句内变速，现明确拒绝并建议按速度分段或使用采样器，不静默按首个速度生成。

### 检查失败状态与数据所有权

原片保存后继续检查的对象曾与持久状态共用内部指针。现存储独立快照；转换器或提取异常会持久保存为失败并写出原因，不停留在“检查中”。派生文件丢失可以从摘要一致的原片重新适配，不被旧派生文件的摘要阻断。

### 新候选遮蔽旧版本

同声部新候选尚未确认时，继续使用已有已确认版本。拼合预检对选定的原片和派生文件进行完整性检查，损坏素材提前报告。

### 合唱尾部切断

用户试听约 9 秒合唱，确认是无词哼唱、总体顺畅，但指出最后一个音像被切断。旧适配片最后 0.1 秒 RMS 约 0.10272，原片最后 0.1 秒约 0.04019；区段结束时仍有明显发声。

仅把请求余量由 0.5 秒改为 2 秒，模型仍可能唱到预算上限，不能作为修复完成的依据。新适配器在不修改主体音符的前提下，把预算内可表示的收尾休止写入 ABC，同时检查谱条件无词合唱区段末尾的信号。

结尾检查使用最后 0.1 秒 RMS，相对峰值及绝对底线识别仍明显发声的边界。它只提供可测量的警示，**不证明最后一个音唱对、没有漏音或音乐句法完整**；本轮只对需要收束的谱条件无词合唱作采用门槛，不把该阈值套到环境音或全部器乐。

## 实际模型证据

硬件：RTX 4060 Laptop 8 GB；音频内核 v0.9.1 CUDA 13；模型和原片只存本地研究目录，未将用户作品数据库、密钥或音频提交公共源码。

| 任务 | 实际结果 | 判定 |
| --- | --- | --- |
| YuE2 Q8，3/9/30 秒研究请求 | 返回约 3.519/9.519/30.519 秒，均有语义截断标志 | 请求限长有效，不能等同于乐句完整 |
| 当前 9.23 秒箫工程，代表音高 MIDI 81 | 修正单音谱后，三次候选稳定窗口仍不足；适配后部分测得 MIDI 69 或 57 | 未通过，不登记错误根音，不以移调冒充成功 |
| 当前作品 9 秒无词合唱，0.5 秒余量 | 返回 9.519 秒；用户认可哼唱音色，但指出尾部切断 | 不采用此候选 |
| 相同合唱，2 秒余量但无显式谱面休止 | 返回约 10.999 秒，较晚区段仍持续发声 | 不能单凭延长请求放行 |
| 相同合唱，显式休止＋2 秒余量 | 返回约 10.999 秒；选取 0.2 秒偏移、9 秒主体＋1.5 秒尾音，本地检查通过 | 用户确认收尾自然，但指出前半段音色稍刺；提供保留原片的轻度柔化试听对照，尚未最终采用 |

## 已取得的自动化证据

- 前端完整浏览器回归：149/149，通过单进程单 worker 执行，包括此前并行失败的助手、历史、时间线与普通编曲用例。
- 前端 lint 与生产构建通过。
- 完整 Go 竞态测试在快照、缓存、候选优先级、结尾休止与结尾检查修复后通过（`go-race-release-check.log`）；这证明代码回归，不证明模型音色质量。
- Windows ServiceChecks、UpdateChecks 以 `dotnet run --self-contained true --runtime win-x64` 运行通过。系统仅有 .NET 10 共享运行时，直接运行要求 .NET 8 的检查失败是环境原因，现已通过自包含运行解决。
- 发布说明脚本的两项测试通过。
- 定向测试覆盖精确单音条件、收尾休止不改主体、变速拒绝、相关缓存失效、合唱默认设置、候选快照、检查失败收尾、派生文件修复、已确认版本优先、文件摘要及持续发声结尾拦截。

合成测试信号只用于证明技术链路，不证明真实模型已生成合格的箫、琵琶或合唱。

## 尚未满足的交付门槛

1. 当前箫所需精确音高、力度和持续时长的真实 AI 采样仍须通过；琵琶挑弹与轮指也不能以错误候选或重复普通挑弹代替。
2. 新合唱候选须通过结尾试听；用户不需要懂乐谱才能提供“自然结束／突然中断”的反馈。曲谱事件的技术核对由软件与开发验收承担，不能要求用户为模型准确性作不懂的保证。
3. 真实 AI 音色入库、跨作品复用、按谱演奏和可编辑示范工程需要实际素材验收。现有技术测试不能代替此门槛。
4. 新修订通过最终 Go/前端与 Windows 检查后，才制作正式完整包及更新包、校验文件并覆盖同一安装；当前运行中的用户程序保持不动。
5. GitHub 可保存明确标注“开发中”的源码检查点；完整 Release 和本轮完成声明需等待上述门槛。
